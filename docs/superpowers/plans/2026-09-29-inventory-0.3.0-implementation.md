# Inventory 0.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Trasformare Inventory 0.2.0 nella prima versione funzionale 0.3.0 con Dashboard reale, gestione Beni e registrazione atomica dei Movimenti, preservando dati, confini di dominio e compatibilità Joomla esistente.

**Architecture:** Il backend resta MVC Joomla moderno e mantiene `items.quantity` come saldo corrente e `movements` come storico append-only. La variazione di stock passa da un servizio transazionale dedicato che valida ACL/input, blocca l'item durante l'aggiornamento, impedisce quantità negative e registra movimento + nuovo saldo nella stessa transazione. La UI usa toolbar Joomla, Form API, Web Asset Manager, Language e layout responsive senza introdurre dipendenze private verso altri componenti.

**Tech Stack:** PHP/Joomla MVC, DatabaseInterface, Form API, Toolbar, ACL, CSRF, Web Asset Manager, SQL MySQL/MariaDB, CSS amministrazione, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-29-inventory-0.3.0-design.md`

## Global Constraints

- Prodotto: `com_xdecaroinventory`; package: `pkg_xdecaroinventory`.
- Namespace stabile: `xdecaro\\Component\\Inventory`.
- Tabelle esclusivamente `#__xdecaroinventory_*`.
- Aggiornamento 0.2.0 -> 0.3.0 non distruttivo; nessun `DROP` o `TRUNCATE`.
- `Inventory -> Core`; mai `Core -> Inventory` e mai accesso diretto a tabelle private di altri prodotti.
- Movimenti inventariali append-only nelle operazioni normali.
- Stock negativo non consentito in 0.3.0.
- Tutte le mutazioni devono verificare ACL e token CSRF lato server.
- Tutti gli input devono essere filtrati/validati; output escapato; query bindate tramite `DatabaseInterface`.
- Test runtime principale su Joomla 6.1.3; non restringere inutilmente la compatibilità dichiarata attuale Joomla 5/6 durante questo rilascio.
- UI coerente xdecaro, responsive desktop/tablet/mobile, light/dark mode, stringhe traducibili tramite Language.

## Review Focus

- Due movimenti concorrenti sullo stesso bene non devono produrre saldo incoerente: test transazionale/locking nel Task 4.
- Un movimento che porta il saldo sotto zero deve fallire senza inserimento parziale: test rollback nel Task 4.
- Lo SKU duplicato deve essere rifiutato con errore comprensibile senza corrompere il record esistente: test nel Task 3.
- Modifica di un bene esistente non deve permettere variazioni arbitrarie di `quantity`: test nel Task 3.
- Richieste di salvataggio senza ACL o CSRF devono essere respinte lato server: test nel Task 2 e Task 4.
